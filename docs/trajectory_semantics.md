# Trajectory and generation contract

## What a branch means

The two axes are **generated token position `k`** and **recurrent depth `t`**.
For each next-token computation:

1. Embed the entire current prefix: prompt plus the method's generated tokens.
2. Run shared recurrent steps, then fork A and seeded donor branches.
3. Continue/intervene/exit within this prefix's computation and read out a token.
4. Append that token, re-embed, and re-fork for position `k+1`.

Hidden states do not persist across generated tokens. This is a cache-free
full-prefix experiment, not a set of persistent conversational agents. Shared
weights and distinct perturbed tensors do not prove different semantic strategies.
Consequently, an intervention affects subsequent generated positions only through
the emitted prefix. If two methods emit the same tokens, there is no extra carried
hidden-state memory of an earlier intervention at the next position. Its return
and continued recurrence occur **inside the current token's depth unroll**.

## What can be compared

For local operator attribution, hold prefix token IDs, attention mask, positions,
depth, receiving state and donor fixed. A fixed-prefix intervention comparison
does not measure free-running answer accuracy. Conversely, once methods emit
different tokens, equal token/depth indices do not identify equal latent contexts.
Do not subtract their hidden states and interpret the result as a controlled effect.

New records contain `prompt_token_ids`, `generated_token_ids`, `prompt_format`,
`trajectory_semantics`, output budget and `stop_reason`. Each token ledger contains
the exact prefix's SHA-256, length, branch seed and recurrent snapshots. The seed
is `seed + 131*k`; branch histories are new at each position. Historical recordings
are unchanged and do not gain invented hashes or snapshots.

## Prompt and stopping policies

The existing experiment configurations remain **raw short-answer prompts**:
first newline, a legacy one-token Boolean rule, EOS or the output-token budget.
EOS now stops immediately even when its decoded text is empty. A budget must be
positive. `max_output_tokens` as a termination reason means budget exhaustion,
not evidence that the model finished its answer.

The calibration script additionally invokes the same decoder with explicit
`prompt_format="chat"`: the pinned tokenizer's chat template,
`add_generation_prompt=True`, `enable_thinking=False`. This omits the template's
requested thinking prefix; it does **not** guarantee that the model will not
generate reasoning. Chat decoding permits newlines and the raw Boolean rule does
not apply; it stops at EOS or its budget. This is a diagnostic mode, not a silent
change to all experiment configs or controller training inputs.

FLOP estimates in new records sum each token's recurrent calls at its actual
prefix length. They remain approximations, exclude separately reported scoring
calls, and do not certify compute-matched system comparisons.

## Baseline calibration protocol

Before a held-out campaign, compare prompt/budget effects on **pilot** problems,
without tuning on the test set. The first diagnostic fixes seed `20261031`, one
problem per arithmetic/logic/graph family, four-depth BF16 forced-final Ouro, and
three policies: raw/2 tokens, raw/64 tokens, chat/128 tokens. The same canonical
decoder is used, including measured inference/scoring call accounting.

The legacy validator extracts an integer from text. That is insufficient evidence
of a completed answer when a chat continuation contains reasoning. Calibration
therefore separately reports whether the **whole response** is an integer and
whether that integer is correct. Budget exhaustion and malformed output must
remain visible even if the legacy first-integer score happens to match.

Reproduction (exact checkpoint required locally; output must not already exist):

```bash
uv run pytest -q tests/test_generation_semantics.py
uv run python scripts/calibrate_ouro_baseline.py --output /tmp/ouro-calibration-new.json
```

This tiny diagnostic cannot establish baseline competence, a best prompt, a
precision-invariant result or intervention efficacy. Choose and freeze the final
answer-extraction/completion policy before a new held-out evaluation. Neither the
historical accuracy tables nor controller checkpoints are regenerated by calibration.

## Observed pilot diagnostic and completion gate

The [initial record](../reports/ouro_baseline_calibration.json) contains all nine
evaluations on the same three pilot problems. Raw/2 and raw/64 both score **1/3**;
the longer raw budget reaches a newline on arithmetic and graph without changing
their wrong answers. All three chat/128 responses start explicit thinking and
exhaust their budget before a final answer. Their first integer must not be scored
as the answer. This is a protocol warning, not evidence that completed chat is
better or worse.

Because all chat cases were unfinished, a separate native-generation follow-up
uses **the same three problems**, a 2048-token ceiling, greedy forced-depth-4
readout and disabled caching. It counts actual native normalization boundaries
and compares its initial token prefix with the adapter's recorded continuation.
It only scores an integer after EOS and outside a completed `</think>` region.
This adaptive budget extension is exploratory, not preregistered or held out.

```bash
uv run pytest -q tests/test_native_generation.py
uv run python scripts/complete_ouro_baseline.py --output /tmp/ouro-completion-new.json
```

Point B's completion gate remains open until that follow-up is inspected. No
operator/control study or controller retraining begins while it is open.
